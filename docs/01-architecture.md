# 01 · 系统架构：AI 研究员 + 确定性分发

MacroRadar 是一个**宏观事件哨兵**：跟踪美联储关键事件（FOMC / CPI / NFP / PCE），
把研究结论渲染成卡片，推送给订阅者。它服务的是"关注投资但不做专业宏观研究"的读者。

本文讲它为什么长成现在这样——两个截然不同的半场，各自用对了工具。

## 一、为什么要把系统劈成两半

| | 研究半场 | 分发半场 |
|---|---|---|
| 输入 | 公开信息（市场行情、FedWatch 概率、投行观点、其他央行） | 一份 HTML + 订阅者名单 |
| 本质 | **开放式检索 + 判断** | **确定性执行** |
| 工具 | AI Agent（带严格纪律） | 模板 + 脚本 |
| 失效代价 | 一条消息内容有误（可纠正、可标注） | 消息发错人 / 漏发 / 重复发（不可撤回） |
| 设计目标 | 覆盖 + 诚实 | 可预测 + 可复核 |

把这两半混在一起——比如让 AI 自由决定"发给谁、发几次"——是这类系统最常见的
架构错误。**研究可以模糊，分发必须确定。**

## 二、四条产品线

| 产品 | 调度 | 触发条件 | 内容职责（防重复是硬约束） |
|---|---|---|---|
| 每日宏观日报 | 工作日 07:00 | 每天必发 | 全景晨报：隔夜市场 + 利率现状 + 今日/本周事件 + 投行视角 |
| T-1 事件提醒 | 工作日 09:00 | 明天有 P0 事件才发，否则**静默** | 赛前简报：单一事件的档案 / 三种情景 / 关键看点（**不放**当前利率与 FedWatch 概率条） |
| 晚间数据快报 | 事件发布后 +30min | 当天有 CPI/NFP/PCE 才发 | 数据复盘：实际值 vs 预期 vs 前值 + 鹰鸽判定 |
| 每周摘要与利率路径 | 周六 09:00 | 每周必发 | 周度回顾 + 下周关注 + 利率路径跟踪；概率较上周变化 >10pp 时额外推「利率突变提醒」 |

四条线的**职责边界是被显式定义过的**（"T-1 不放概率条"这类规则写进产品说明），
因为当多个自动化读同一批数据时，重复内容是比错误内容更常见的退化方式。

## 三、执行流（每条线一致）

```
① 读日历  data/calendar.json        → 今天/明天/本周有哪些事件？优先级？
② 研究     AI Agent（WebSearch）     → 抓真实数值，按 docs/03 的纪律标注来源
③ 渲染     读 templates/ → 填数据    → 落盘 reports/<date>-<kind>.html
④ 选人     读订阅名单（本仓库为 data/subscribers.csv） → 过滤 → 只取「启用」且勾选了本频道的行
⑤ 分发     scripts/send.py           → 邮件（主线）/ PushPlus（中国可选）
⑥ 判据     退出码 0 且 ok=true        → 才算完成；否则视为失败并暴露
```

第 ⑥ 步不是形式主义：**"部署 ≠ 流程结束"** 是这个系统踩出来的教训
（见 `04-delivery-and-deployment.md`）。

**两个数据文件的角色**（避免"这个文件谁在用"的疑问）：

| 文件 | 谁写 | 谁读 | 用途 |
|---|---|---|---|
| `data/calendar.json` | 人工维护 / `tools/build_calendar.py` | 四条产品线 + `tools/tz_convert.py` | 事件时刻与优先级（同时存 `date_et` 与 `date_bj`） |
| `data/fedwatch_history.json` | 研究腿每次运行后追加一条 snapshot | 周报 | 计算"概率较上周变化 >10pp"，触发「利率突变提醒」 |

本仓库的示例代码只消费 `calendar.json`（渲染与换算不依赖历史快照）；
`fedwatch_history.json` 的读写发生在研究腿——它是四条产品线里唯一跨周依赖的数据。

## 四、三条设计原则

### 1. 单一事实源（Single Source of Truth）

- 样式只维护在 `templates/` ——改模板，所有产品同时生效，自动化 prompt 不动；
- 订阅者只在订阅表里维护——增删人不改代码、不改 prompt；
- 事件日历只在 `data/calendar.json` 里维护——全局背景（当前利率、主席、regime）也在这。

**任何"两处都要改"的设计都是 bug 温床。**

### 2. 数据与要展示的结构分离

AI 只负责"填数据"，不负责"决定结构"（5 个区块的顺序是固化的）。
这既保证视觉一致性，也让 AI 的输出可校验：填充错了容易发现，
结构被自由发挥则每次都要重新审。

### 3. 静默是合法状态

T-1 没有事件就**不发**，快报没有数据就**不发**。
"每天必须有点动静"的自动化会制造噪声，噪声会让订阅者关掉通知——
而关掉通知的哨兵等于不存在。

## 五、仓库里这份实现与生产系统的差异

| 项 | 生产系统 | 本仓库 |
|---|---|---|
| 订阅者来源 | 在线表格（腾讯文档 smartsheet） | 本地 CSV（`data/subscribers.example.csv`） |
| 调度 | 宿主平台的四条自动化 | 自备 cron / 任务计划（**docs/04 第六节给出示例**） |
| 邮件凭据 | 本地 `config/smtp.json` | `config/smtp.example.json` 模板，自行填写 |
| PushPlus | 主力推送通道（微信） | **可选适配器**，见 docs/04 |
| 样张 | 全部历史产出 | 精选 4 份真实产出（`samples/`） |

泛化的原则很简单：**把"我的账号 / 我的名单 / 我的机器"从系统里拆出去，
剩下的就是可以开源的部分。**

## 六、为什么不直接用现成轮子

这套系统的三个"商品化层次"其实都有成熟方案，我们**一个都没采用**——理由要写清楚，
否则会被读成"没调研"：

| 层次 | 现成方案 | 不采用的理由 |
|---|---|---|
| FedWatch 概率 | [`pyfedwatch`](https://github.com/ARahimiQuant/pyfedwatch)（55★） | 它解决"从 CME 工具算概率"；而本项目要的是"连带投行观点、其他央行、事件改期一起判断"，那一层只有 AI 能覆盖。用了它也省不掉研究腿 |
| 日历解析 | [`forex_factory_calendar_news_scraper`](https://github.com/fizahkhalid/forex_factory_calendar_news_scraper)（103★） | 全量日历是噪声源：本项目只需 P0 事件 + 北京时间标签，手工维护 40KB JSON 反而更准、更可控 |
| 多通道推送 | [`push-all-in-one`](https://github.com/CaoMeiYouRen/push-all-in-one)（211★） | 只需要两条通道（SMTP + PushPlus），引一个 SDK 换不来收益；且分发半场要求"零依赖、十年后仍能跑" |

**代价要说明白**：这些取舍让系统**强依赖 AI 研究腿**——没有 agent 就没有数据。
这是一次有意识的交换：用"可移植性"换"半结构化信息的覆盖能力"。
想要纯确定性数据链路的读者，请用上表的现成方案，或自行把它们接进 `data/` 层。
